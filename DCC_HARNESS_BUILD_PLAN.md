Build a system that helps an agent produce and revise detailed environments while preserving assets, materials, lighting and project intent over long work sessions. The intended entry point remains the artist's normal Claude Code, Codex or Cursor chat.

First establish whether explicit skills and measured feedback improve creative results enough to justify a harness. Begin with one artist, one Windows machine, one Blender writer and an existing MCP transport. Save task checkpoints and keep a log immediately. Add durable execution machinery when moving beyond supervised experiments.

The earlier plan put too much engineering before this decision. Its 7–13 week estimate is retired as the starting commitment. The next commitment is a five-working-day experiment, followed by a decision about what deserves implementation.

## Week one creative experiment

Use one representative courtyard corner rather than the entire three-zone environment. Require six to eight asset definitions, including two newly modeled assets, repeated instances, three shared material families, motivated lighting and three fixed inspection cameras. A silhouette-led architectural element and a prop must be built, so importing a library cannot satisfy the whole brief.

Preselect a small asset/texture/HDRI kit and references. Give each condition identical inputs, software/model versions, constraints and resource ceilings. The artist sets a short rubric for composition, proportion, material coherence, lighting and editability before seeing outputs.

| Condition | Available method | Question |
|---|---|---|
| A Plain MCP | Normal agent brief and existing Blender tools | What does the current setup achieve? |
| B Focused skills | A plus three practical process skills and task checkpoints | Do instructions and a repeatable review method improve results? |
| C Minimal measured loop | B plus native measurement/assert helpers and a structured change report | Does executable feedback add value beyond the skills? |

Run two independent trials per condition, six runs initially. Randomize execution order and hide condition labels during artist comparison. Each trial starts from a fresh copy of the same starter file, without another run's generated assets or transcript. Evaluate every condition with the same independent checks; do not let C grade itself more leniently.

Apply the same final revision: change a shared stone material and one hero dimension while retaining layout and the approved lighting. At the same task boundary, replace the chat context and resume from the files. This tests continuity before building a scheduler. Do not inject uncontrolled editor crashes into the initial quality comparison.

### Daily sequence

| Day | Work | Concrete output |
|---|---|---|
| 1 | Restore a live connection, inspect the actual Blender/runtime, fix the starter kit and rubric; begin the plain-MCP baseline | First geometry and images, baseline failures and render timing |
| 2 | Adapt three skills to existing callable tools; run the skills condition | A complete small environment and revised version |
| 3 | Add only the measurement helper needed for observed failures; run C | Comparable output plus native measurements and declared change coverage |
| 4 | Complete second trials, context replacement, late revisions and native reopen checks | Six comparable result packages |
| 5 | Artist review, cost analysis and investment decision | Chosen minimum product scope and a ranked defect list |

If a native helper cannot be completed within its timebox, report C as incomplete and evaluate A/B. Do not substitute a week of framework selection for a creative result.

### Three initial skills

1. **Plan an environment task:** translate references into a small brief, asset list, dimensions, shared materials, fixed views, preserved features and an acceptance checklist.
2. **Build, measure and revise:** construct task-sized deliverables, inspect applicable native properties, compare against the brief and save checkpoints. New deliverables require an expected missing-deliverable failure before construction; existing work requires a passing baseline and preservation checks.
3. **Review and continue:** collect comparable images, identify specific defects, perform a bounded repair, record decisions and produce a continuation packet.

Adapt the useful content already in `dcc-skills/`; keep the source files intact. Write the runnable trial variants in the existing simple SKILL.md format. Use actual MCP actions or a named helper script, not the unimplemented assertion/history APIs shown in the original examples. Schema registries and thirteen separate discipline packages are not prerequisites.

Also use selected methods from `blender-game-skills` and `cc-blender-skill`, as mapped in the [skill catalog](./DCC_HARNESS_SKILL_SYSTEM.md#selective-reuse-from-the-two-additional-skill-libraries). Borrow reference calibration, modeling/material recipes and evidence-based review; keep the harness as the single entry point. Freeze the adapted instructions before comparison. B receives the written methods; C adds only the relevant executable measurements. Independent evaluation remains identical for A/B/C. Orthographic silhouette helpers are optional for an asset with suitable references, not a new environment-wide gate. Do not add either repository's complete pipeline, global world reset, automatic skill-rewriting loop or render schedule to week one.

### Budget and capture policy

These are proposed initial ceilings to adjust once the Day 1 timing probe is available. Freeze the settings before comparing conditions; a changed budget creates a new comparison round.

| Resource | Initial ceiling |
|---|---|
| Agent/native work per trial | 90 minutes including a reserved 15-minute late revision |
| Metered model and generation spend | USD 25 per trial; USD 150 across the initial six |
| Rendering within the trial | 30 minutes total; stop at the time cap even if image count remains |
| Native still captures | At most 24 per trial, normally 960×540 |
| Repair attempts | At most two materially different repairs of the same failed requirement |
| External generation | None in this first comparison; use the fixed asset kit |
| Artist review | Record separately; target at most 30 minutes per condition |

Capture the three full views at blockout, surface/lighting completion, pre-revision acceptance and after the revision. Use remaining captures for changed regions. Reuse valid baseline images. Do not render every view after every primitive or spawn a critic after every operation.

Calibrate one render preset on Day 1; use it across the comparison. Record actual input/output tokens, available billed usage, wall time, rendering time, tool calls, repair count and artist repair time. Where a client does not expose metered cost, report usage and cost as unavailable; do not treat a subscription run as zero cost or manufacture a dollar total. A condition with unmeasured spend cannot claim a cost advantage.

### Proceed, narrow or stop

Record both pre-revision and post-revision results. A candidate passes the practical quality gate only if both trials reopen with dependencies, preserve the specified locks, have no critical missing requirement, and the artist rates the result usable with minor cleanup. Use a five-point rubric with 4 meaning that level and 5 meaning accepted without required cleanup.

Promote C beyond a prototype only if it meets that gate and, relative to B, either the artist prefers both paired outputs or artist repair time falls by at least 25% without worse quality. These small-sample thresholds are investment rules, not statistical proof. Confirm the chosen approach on an unseen brief before broader development.

If B performs as well as C, deliver the skill package first and defer the runtime. If A is equally usable, keep the simpler workflow. If no condition is acceptable after one bounded method revision and a repeat comparison, stop infrastructure expansion and revisit task scope, asset strategy or modeling methods. If results are mixed, collect a limited additional comparison; do not infer success from the best image.

The held-out comparison is a separate four-run allowance, not hidden in the initial budget. Its proposed ceilings add at most USD 100 and six hours of trial work.

## Minimum implementation for the experiment

Use the existing MCP already exposed in the current client, once its live bridge works. Timebox connection diagnosis and suitability to half a day. Escalate a concrete missing capability rather than automatically evaluating several frameworks. DCC-MCP core remains a later candidate only if a measured gap makes adopting it cheaper than a targeted helper.

The helper is real Blender-side code. Start as a versioned Python module loaded through the existing execution tool. It measures the selected native data, evaluates constraints, captures supported before/after changes and reports observation coverage. Package it as an add-on if persistent callbacks or installation lifecycle justify that step.

Initial observations cover world-space bounds and units, dimensions, collection/parent relationships, mesh/material bindings, declared geometry/UV fields, texture dependencies and material parameters used by the pilot. Broader node, animation and simulation fingerprints come when tasks need them. A report must distinguish measured changes from merely declared targets.

Keep a brief, style record, task checklist, append-only operation log, native checkpoints and evidence sidecars in the project. Log the planned call before dispatch and record its observed result afterward. Save to a new filename at each accepted task boundary. A timed-out write becomes unresolved: inspect it before continuing, or restore a known checkpoint of the owned file. No automatic replay of arbitrary code.

This supervised prototype makes no promise that every write is intercepted. Its purpose is to test quality and continuity cheaply. The exact upgrade to managed execution is specified once in [decision D4](./DESIGN_DECISIONS.md#d4-operation-identity-and-retry-ownership).

## Asset files and native identity

For the first experiment, use one owned GUI Blender session and one evolving master file. The artist reviews in that session; pause generation before manual edits. A separate rendering process may read a saved immutable checkpoint and write images, but must never save over the authoring file.

As soon as independent asset workers are introduced, each writes a separate versioned asset file. The single assembly writer links published collections into a versioned master. Its local collection-instance objects carry placement; source geometry and materials stay in immutable libraries. Artist changes to linked content require an explicit new asset version or a recorded override. Relative dependencies are included in the handoff.

Blender documents linked references, collection instances and overrides; linking and appending have different update behavior. The project should select these deliberately. [Blender Link and Append](https://docs.blender.org/manual/en/5.0/files/linked_libraries/link_append.html)

Keep asset-definition identity separate from local instance identity. Detect duplicated custom IDs after copy/import and before checkpointing. Preserve the source asset identity where sharing is intended, but assign a new local instance identity to the new placement. If the original cannot be identified from the prior registry, stop the affected binding rather than guessing.

For the pilot, ordinary objects and collection instances are sufficient. Geometry Nodes distributions are later identified by generator identity, recipe version and an explicit stable point key. Without a stable key, address the distribution as a versioned whole and invalidate per-instance annotations after regeneration. The ID node can fall back to an index when no id attribute exists; that is not a persistent global asset identity. [Blender ID node](https://docs.blender.org/manual/en/5.2/modeling/geometry_nodes/geometry/read/id.html)

## Textures and asset intake

The pilot uses two material paths: procedural node materials for simple paint/metal and controlled variation; fixed PBR texture sets for stone or ground. Specify physical texture scale, UV or projection method, channel/color-space mapping, normal orientation, roughness range and one common look-development view. Record shared material versions before assigning them.

Use a small preselected Poly Haven kit for HDRIs, textures and optional secondary props. The provider identifies its assets as CC0; retain source URLs, asset identifiers, downloaded-file hashes and the license record anyway. Site/API access terms are distinct from the asset license; use ordinary downloads or a permitted integration. [Poly Haven asset license](https://polyhaven.com/license)

Intake checks units, orientation, dimensions, visible silhouette, material slots, texture resolution, missing dependencies and approximate memory/geometry cost. Copy assets into the project kit and pin that kit for all trials. Do not introduce arbitrary online assets halfway through one condition.

Defer painted hero textures, high-to-low bakes, UDIM workflows and generated textures until the pilot reveals a need. Each needs its own authoring tool, source retention and quality checks. A generated texture also needs provenance and cross-view seam/consistency review. These are separate later implementations, not one unspecified texturing capability.

## Rendering and evaluation

Start with the GUI review loop already needed for artist feedback. Viewport captures record their actual view settings; final comparison captures use fixed native cameras and a common renderer/color configuration.

A background render is not a viewport screenshot. Qualify the intended render backend on the exact machine using a saved fixture. Choose background Cycles or a separate owned GUI review process according to measured availability and cost; do not assume every viewport API works headlessly, or dismiss all headless rendering as broken. [Blender viewport rendering](https://docs.blender.org/manual/en/latest/editors/3dview/viewport_render.html)

Keep desired state separate from observed state. Evidence identifies the native checkpoint, relevant dependencies, camera, frame, lighting and color configuration. Invalidate only evidence affected by a change. Hard constraints and aesthetic judgments remain separate: passing dimensional tests does not establish good composition.

Use task-specific topology and UV policies. Keep mode-filtered tools as steering while recognizing that filtering alone does not enforce permissions. Retain the strongest accepted candidate when repairs fail. Record routine decisions within authorized scope; ask the artist when a decision changes the brief or an approved constraint.

## Gated expansion after the experiment

| Stage | Scope | Gate |
|---|---|---|
| A Creative experiment | Five working days, three skills, small native helper and six trials | Choose the minimum method that produces acceptable results |
| B Continuity prototype | Roughly 1–2 weeks if justified; minimal durable journal, prepare/execute, save/reopen and one client entry point | Held-out brief succeeds; fresh context resumes; duplicate dispatch and lost response cause no blind replay |
| C Detailed environment | Roughly 1–2 weeks initially; three zones, 12–20 assets, 4–6 material families, six views and linked asset publishing | Artist accepts output and a late shared-material, hero-size and layout revision; unrelated work is preserved |
| D Unattended operation | Estimate from B/C failures; one runner, owned workers, recovery and resource limits | Repeated two-hour runs pass, then eight-hour runs with injected faults; 24 hours only when justified |
| E Broader access and disciplines | Package additional clients, add motion exercises and a second DCC as needed | Same project survives client changes; native transfers and temporal work pass their own quality gates |

Before D, test restart after dispatch, crash during save, lost replies, manual edits, budget exhaustion and unresolved external effects. Extend the local journal and worker fencing only as needed to pass those tests. One executor owns retries; embedded adapter-flow retries stay disabled for mutations unless explicitly qualified under that executor.

Use the current host for A/B. This planning chat is Codex; Claude's review was supplied as an external document. The skills and CLI should remain usable from Claude Code without requiring a marketplace package. Additional installers, controller handoff between clients, a custom review UI, SDK runners and the early Unreal contract exercise are deferred behind the creative gate.

The product direction remains a plugin plus a persistent local harness above existing MCP servers. Build its breadth from demonstrated needs: environment continuity first, then longer unattended work, motion design and additional DCCs.
