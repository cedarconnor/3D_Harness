# Longer continuity comparison

The artist preferred both plain-MCP outputs in the short comparison and noted that longer development is the intended use. This experiment therefore compares the plain workflow against a minimal continuity prototype, using identical native starting files and the same sequence of 16 requests. It tests accumulated work and context loss; wall-clock duration alone is not the outcome.

Four workflows comprise two randomized blocks, each containing one plain-MCP run and one continuity run. Each workflow uses four new agent conversations, with no inherited coordinator history. One live Blender writer operates at a time. The common starting file is the revised version of the artist's preferred courtyard, with only three fixed review cameras added. The original file is preserved. Its user preference is not treated as a completed editability or production acceptance assessment.

| Session | Requests and challenge |
|---|---|
| 1 | Add a connected forecourt and garden, potting table and shared stools |
| 2 | Add a pergola, shared planted pots, birdbath and working props |
| 3 | Preserve a scripted artist placement edit; revise shared stone, table and stools; add wayfinding |
| 4 | Reconcile a deliberately withheld acknowledgement; add lanterns, revise signage and complete handoff |

The artist-edit event is a controlled proxy, not an actual manual user edit. The lost-acknowledgement event leaves an actual native plaque and, in the continuity method, an unresolved operation record. Both workflows receive the same intended operation and uncertain-outcome notice. Agents must inspect the native result. No editor crash, process kill or real network failure is claimed.

Each session has a 20-minute authoring ceiling and at most 4 production captures. Each workflow therefore allows 80 minutes of authoring and 16 agent captures, plus 24 independent captures and an initial shared baseline capture set. Stop at 30 minutes of aggregate timed rendering per workflow. Tokens and dollar cost are recorded only if available. All four workflows, including failures and incomplete stages, remain in the results. No selective retries, comparative feedback or additional coaching is allowed after freezing inputs.

The plain method receives the native file, current requests and machine-readable contract, common decisions, a current native observation, prior handoff and any event notice. The continuity method receives the same creative inputs plus immutable state history and the small observation/check/journal package. No extra aesthetic recipes are provided. Supplying the same current observation avoids withholding known facts from the baseline; this experiment tests the additional executable checks and accumulated state. It contrasts the new continuity prototype with the plain workflow and is not a rerun of the earlier three-condition experiment.

Measure cumulative requirement failures, unintended native changes, lost decisions, preservation of the artist edit, duplicate recovery effects, unresolved journal operations, phase completion and authoring/recovery effort. Images are evaluated separately for style coherence, composition and visible regressions. Artist repair time and editability remain unmeasured until direct review. Native checks cover selected fields and cannot establish arbitrary modifier semantics, geometry quality, collisions, animation or artistic acceptance.

The new store retains versioned native checkpoints, observation and check records, cumulative decisions, asset/material users, dependency records and newly accepted journal evidence. Hashes and parent links are verified before continuation. Stale parents, duplicate steps, pending writes, changed evidence and partial publication are rejected. It remains an advisory single-writer layer over the existing MCP: no daemon, tool interception, native-save transaction, concurrency fencing or general exactly-once guarantee has been implemented.

A successful result would justify the next narrow implementation only if the continuity workflow preserves quality and reduces measured drift, recovery failures or artist repair effort across both repeats. A larger scene or more files alone is not a benefit. Two repeats inform a development decision, not statistical superiority. Shared filesystem/tools and ambient skill descriptions mean isolation is procedural; this remains a single-blind artist comparison.
