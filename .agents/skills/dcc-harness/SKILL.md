# Work in a persistent DCC project

Use the installed `dcc-harness` command, the combined `dcc-harness-mcp` endpoint, or `python -m dcc_harness` from this repository. The combined package bundles these skills and their references; copying a skill folder alone is not a complete installation. Read [combined MCP operation](../../../docs/guides/COMBINED_MCP.md) for setup and [the everyday workflow](../../../docs/guides/EVERYDAY_WORKFLOW.md) for advisory CLI arguments.

**Managed projects:** the [managed execution guide](../../../docs/guides/MANAGED_EXECUTION.md) takes precedence over the advisory reservation instructions below. Follow `brief`/`next`, submit with `run-submit`, and execute/reconcile through the project's backend. Background runs use `run-execute`/`run-reconcile`; paired open scenes use `blender_execute`/`blender_job` or `live-execute`/`live-reconcile`. Do not call `begin-edit`/`finish-edit` or an unrelated live-write MCP for managed projects. Autonomous mode advances evidence-backed stages within the brief; approval-gated mode waits for the artist's own terminal. Never manufacture artist approval.

**Open scene:** read [live Blender operation](../../../docs/guides/LIVE_BLENDER.md), discover the explicit session, select its scene, and inspect stable target IDs before editing. Attach into a new live project. Never infer a target from selection or reuse a preparation across file reloads. Lost replies require status inspection; external edits require explicit refresh. Preview renders are evidence to inspect, not approval. Unsupported contexts and unqualified add-ons remain explicit stops.

**Start every session with `brief PROJECT`.** It prints where the project stands and the permitted next steps with commands already filled from the verified record, plus open feedback, stages, the recorded brief, the latest handoff and the rules below in short. Run it again after any command that changes the project. `next PROJECT` gives the same steps as JSON, and `requirements PROJECT STAGE` gives a stage submission skeleton. [The agent quick reference](../../../docs/guides/AGENT_QUICK_REFERENCE.md) has the exact command sequences and payload shapes; read the longer guides only for cases it doesn't cover.

For an existing continuity project, run `resume PROJECT --focus ID...` before authoring when you need an object's measured fields. It verifies the checkpoint chain and returns the brief, retained decisions, handoff, pending edits and scoped shared users. `RECONCILE` means inspect the saved/native outcome; it does not authorize replay. An existing untracked .blend is input for a new project, not a reason to overwrite a previous store.

If resume includes `coordination`, inspect its outstanding feedback and eligible environment stages. Read that project's pinned skill copies under `pinned_files_root`; do not silently substitute newer repository instructions. See [structured feedback](../../../docs/guides/STRUCTURED_FEEDBACK.md) for binding and exact commands. Routine stages can use agent review within the accepted brief; explicit artist gates remain separate. A changed runtime or partial record requires inspection, not an invented approval.

For a new project, inspect the intended Blender instance, record the brief/decisions, save an owned native checkpoint and observe it with `observe SAVED.blend --blender PATH --output-dir NEW_FOLDER`. In a background Blender script, `dcc_harness.continuity_blender.observe()` is equivalent straight after opening or saving the file; an interactive session observes `native_dirty: true`, because Blender does not mark edits made from Python as modified. Use `fill-hashes` to complete `{path}` references in coordination payloads instead of hashing files by hand. `start` requires clean saved-state evidence. Preserve the artist's current document; use an owned background file when live editing is unnecessary. Initial adoption establishes a baseline, not artistic acceptance.

If that saved scene lacks stable IDs, use [initial scene adoption](../../../docs/guides/SCENE_ADOPTION.md): `adopt-preview` produces a readable plan, then `adopt-apply` applies it to a new file and independently observes the saved result. Inspect the plan within the user's authorized scope. Never guess through duplicate IDs, ambiguous shared assets or outside-scene ownership. `NEEDS_REPAIR` retains a candidate with observation issues; only `READY_FOR_START` is ready for the usual baseline command. This helper does not adopt manual revisions into an existing store.

For large instance-heavy observations, use the optional [compact storage](../../../docs/guides/OBSERVATION_STORAGE.md) when all consumers have runtime 0.4.6 or later. Write new files with `write_json(..., compact_observation=True)` and read them with `evidence.read_json`; full checks still apply. Never repack a retained checkpoint in place or discard UV evidence to shorten a resume.

Load the relevant craft skill only: `dcc-architecture` for construction, `dcc-materials` for surface work, `dcc-environment-assembly` for site/dressing, or `dcc-lighting-review` for camera/light decisions. For general Blender craft beyond these, such as modeling, UVs, Geometry Nodes, rigging, animation, simulation, matchmove and export, pick skills from the [`blender-craft` index](../blender-craft/SKILL.md). The existing `dcc-plan-environment`, `dcc-build-revise` and `dcc-review-continue` govern planning, authoring and evidence. Ordinary work does not require a blind trial or subagents.

Before a scoped edit, save its actual script and continuity contract. `begin-edit` requires the expected parent, current saved file and matching native observation; it reserves the retained script/contract. Execute that retained script once against an owned working copy. A reservation does not execute code. Save a new result, freshly observe it, then use `finish-edit`: it recomputes the frozen contract, retains a rejection or publishes a passing checkpoint plus decisions/handoff. Never edit the accepted native or retained script in place.

Render review images with `render SAVED.blend --blender PATH --output-dir NEW --project PROJECT`, which uses the project's `review_views` decision, never saves, and returns evidence entries; add `--detach` and `render-wait` for long renders. When the project has a `relations` decision, measure the saved result with `relations SAVED.blend --blender PATH --output-dir NEW --project PROJECT --strategy "what this file changes"` before finishing. Read the relation history in `brief` first and never repeat a repair it marks `OPPOSING` or `NO_PROGRESS`; a `CONFLICT` means subjects must be adjusted individually. A `bounds_only` estimate permits inspection, not repair. Inspect required review images before publication. If a numerically valid candidate is visually unsuitable, use `finish-edit --reject-reason "specific visible defect"` to retain it without changing the accepted parent or decisions. The outcome separates `native_check_passed` from publication. A numeric pass must not silently override the reviewer's decision; rejected attempts appear in the next resume packet.

On lost acknowledgement or quota interruption, keep the edit unresolved. Inspect actual effects and supply the observed result to `finish-edit --reconciled`; do not redispatch merely because no reply arrived. Partial metadata or stale locks require manual diagnosis. Automatic crash recovery, external-write interception and background scheduling are not implemented.

For an artist review, build `review-page PROJECT --output-dir NEW --blender PATH` and give the artist its `index.html`; import what they export with `review-import PROJECT EXPORT --page FOLDER`. Add `questions` with defaults to a stage submission the artist must decide on. Only the artist approves: an export with a stage approval, or any payload with the artist as reviewer or authority, is refused from your session. Hand the artist the exact command for their own terminal, and never claim the artist role or work around the refusal. When an artist note shows an error no check caught and a rule can measure it, propose a [learned check](../../../docs/guides/LEARNED_CHECKS.md) with `check-propose`; taste stays project direction, and only the owner approves. Pinned checks listed by `requirements` must pass before a stage completes. For your own review, use `review PROJECT`, inspect the referenced whole-scene/detail images, and separate measured preservation from visible quality. Readiness to inspect is not permission to mutate an unknown live editor.

For a deliberate saved manual/MCP edit outside a reservation, use [external revision review](../../../docs/guides/EXTERNAL_REVISIONS.md): prepare a narrow contract, fresh saved observation, handoff and decision updates; `preview-revision` freezes the candidate and reports changed fields/shared material users. Inspect that copy before `accept-revision` with its exact preview hash and a factual review note. This does not repair IDs or settle a pending native operation. Changed parents invalidate previews, and observed external dependencies require a self-contained owned copy. A lost acknowledgement may return `ALREADY_PUBLISHED`; do not rebuild or republish the edit.

When a project has capability policy, inspect `requirements PROJECT STAGE` before choosing a manual approach. Resolve qualified providers against the target and engine; obey explicit require/prefer/fallback policy. Reuse a fresh service receipt instead of dispatching again. Missing required providers or qualification are actionable stops, not permission prompts or reasons to claim manual work satisfies the policy. See [add-on recipes](../../../docs/guides/ADDON_RECIPES.md).
